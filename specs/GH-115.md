# GH-115 — Returns create: item Rejection Reason lost after a rejected Save (found while testing #111)

- Issue: #115
- Reporter: @sbreslaw
- Approver: Reporter (@sbreslaw)
- Triage date: 2026-11-25
- Category: _RET (Returns)
- Order types: ZKR, ZISL, ZWST, ZXFR

## Request (as filed)

> **Steps to reproduce on DH1:**
>
> Found while testing #111 (PR #113).
>
> 1. Create a return, fill the header and one item, and pick a Rejection Reason on the item (sent at once as `SetRejectionReason`).
> 2. Save so that a backend save check rejects it (e.g. ZKR with Return Reason `100`).
> 3. Correct the header and Save again (since #113 this retry saves).
>
> **Actual behaviour:** After the rejected Save the item rows go back to local rows that keep NDC, Lot, Expiration Date, Quantity and Return Reason, but not the Rejection Reason. The Rejection Reason cannot be picked on a local row (it is an action on a saved session row), so the retried return is saved without it. This also happened before #113; it shows now because the retry saves.
>
> **Expected behaviour:** A Rejection Reason picked before a rejected Save is kept and is on the saved return after the retry, or it can be picked again before the retry.
>
> **Acceptance (optional):** _No response_

## Acceptance

The change will be tested against this list.

1. **Kept on screen.** A new ZKR return has one item with a Rejection Reason picked. Save is rejected by a backend save check (for example, Return Reason `100`). The backend message is shown in the message list, and the item row still shows its Rejection Reason next to its other values.
2. **Saved after the retry.** After the header is corrected, Save succeeds. Reopening the saved return (and VA03) shows the item's Rejection Reason. In the network trace:
   - the Rejection Reason (`SetRejectionReason`) is sent on the re-posted item in the new create session before the save request (`SaveChanges`);
   - the save request is sent on its own.
3. **Only where picked.** With two items, only one carrying a Rejection Reason, after the retry only that item has it; the other has none.
4. **Item edited after the rejection.** If an item field is changed after the rejected Save (the session re-opens at once), the Rejection Reason is still applied, and the return saves with it.
5. **Other return types.** The same holds for ZWST, and for ZISL and ZXFR where the backend save checks let a return save (see #114).
6. **Unchanged.**
   - Picking and clearing a Rejection Reason during create (before any Save) and on saved returns works as today.
   - A Save that is not rejected sends the same requests as today.
   - Creating a Provider Order (ZKB) is unchanged.
   - No new console errors.

## Out of scope

- Provider Orders (ZKB, ZREP): their retry after a rejected Save stays as today (open question 3).
- Picking or clearing a Rejection Reason on a row that has not been posted yet (open question 1).
- Keeping the create session open after a rejected save, instead of re-posting the items.
- The backend save checks themselves (what they check and their messages; see #114).

## Open questions

Each question shows the default that is applied if it is not answered.

1. **Keep, or pick again?** The issue accepts either.
   - Default: **keep** the value on the row (shown, not editable there until the return is saved) and apply it again automatically when the row is re-posted.
   - To change it before the retry, the user deletes and re-adds the row; after the save, it can be changed on the saved return.
   - Alternative on request: also allow picking or clearing on rows that are not posted yet.
2. **The backend refuses the Rejection Reason at the retry.** Default: handled like any failed item post at Save. Save stops, nothing is saved, the entries stay, the backend message is shown, and Save can be retried.
3. **Provider Orders too?**
   - Default: **Returns only**.
   - Alternative on request: both.
4. **Forcing a rejected Save for testing.**
   - Default: ZKR with Return Reason `100` while #114 is open.
   - If #114 removes that rejection first, use any other save-check rejection the backend team names.
