# GH-114 — Returns save checks: reject Return Reason / Return Type values the app offers (found while testing #111)

- Issue: #114
- Reporter: @sbreslaw
- Approver: Reporter (@sbreslaw)
- Triage date: 2026-11-25
- Category: _RET (Returns)
- Order types: ZKR, ZISL, ZXFR (ZWST affected by the same check)

## Request (as filed)

> **Steps to reproduce on DH1:**
>
> Found while testing #111 (PR #113). With #113, the header fields reach the create session before `SaveChanges`, so the backend save checks (`USEREXIT_SAVE_DOCUMENT_PREPARE`) now see them. Provider 40029638, NDC 49281-0007-10, one item, all header fields filled.
>
> 1. Create ZKR, Return Type REPL, Return Reason `G99` (the app sets G99 itself when the items have different reasons) or `100` → Save.
> 2. Create ZXFR with any Return Reason from the ZXFR list (`200`–`205`, `G99`) → Save.
> 3. Create ZISL, Return Type REPL (also tried with RETO and RETR in the session), any Return Reason → Save.
>
> **Actual behaviour:**
>
> 1. `ZCRM/182` "Invalid Return Reason value: G99" (same for `100`); `G84` saves.
> 2. `ZCRM/183` "Invalid Wastage Reason value: 200" (same for `201`, `G99`). Reason `101` (a ZWST code, not offered for ZXFR) saves.
> 3. `ZCRM/181` "Return Type cannot be blank", although `ZZ1_VaccineReturnType_SDH` is in the session PATCH and reads back from the session.
>
> Also: every return saved this way gets the order-log entry `ZCRM/51` "MIX is Not Valid for all routine vaccines 49281-0007-10" (the order still saves).
>
> **Expected behaviour:** The save checks accept the Return Reason / Return Type values the app offers for each return type (or the app's lists are aligned with what the checks accept), and ZISL sees the Return Type that is set.
>
> **Acceptance (optional):** _No response_

## Acceptance

The change will be tested against this list.

1. **ZKR saves.** A new ZKR return with one item, Return Type `REPL` and Return Reason `G84` saves on the first Save. So does one more code from the ZKR list (see open question 1).
2. **Mixed reasons save.** A ZKR return with two items with different reasons (the header shows "Multiple Reasons") saves. The header reads `G99`, and each item keeps its own reason. The same holds for ZWST and ZXFR.
3. **ZXFR saves.** A ZXFR return with Transfer Reason `200` saves, with no "Invalid Wastage Reason" message.
4. **ZISL saves with its Return Type.** A ZISL return with Return Type `REPL` and a reason from the ZISL list saves. Reopening it shows Return Type `REPL`, and VA03 shows special processing indicator `REPL`. A new ZKR return likewise stores the picked Return Type, not `01`.
5. **Lists match the checks.** For each of ZKR, ZISL, ZWST and ZXFR, the first and the last code of the Return Reason picker and `G99` are accepted by Save. A code that is not in that type's list is still refused ("Invalid Return Reason" or "Invalid Wastage Reason").
6. **Still refused.**
   - A blank Return Reason is refused ("Return Reason code is required").
   - A blank Return Type on ZKR or ZISL is refused ("Return Type cannot be blank").
7. **No MIX warning on returns.** A saved return has no "MIX is Not Valid…" entry in its order log (open question 4).
8. **Unchanged.**
   - Provider Order (ZKB) save is unchanged, including the MIX warning for a routine vaccine.
   - Editing an existing return is unchanged.

## Out of scope

- Any change in the app. The app's Return Reason and Return Type pickers already read their lists from the backend.
- Correcting existing ZKR returns that were saved with special processing indicator `01` (open question 5).
- Other save checks and order-log messages not named in this spec.
- Releasing returns for follow-up processing before the save.

## Open questions

Each question shows the default that is applied if it is not answered.

1. **Which ZKR / ZISL reasons are valid?** The picker offers all 29 codes; the save check accepts `G81`–`G90`.
   - Default: the check is right. ZKR and ZISL offer `G81`–`G90` plus `G99`, so their picker shrinks from 29 to 11 codes.
   - Alternative: the check accepts all 29 codes.
2. **Is `G99` "Multiple Reasons" a valid header reason at save?**
   - Default: yes, for all four return types. It is already in the ZWST and ZXFR lists, and the app sets it for mixed items.
   - If no: the app needs a different header rule for mixed items (a separate frontend change).
3. **ZWST and ZXFR checked separately.**
   - Default: ZWST accepts its own list (`100`–`104`, `G90`, `G99`) and ZXFR its own (`200`–`205`, `G99`). Best: the check reads the same per-type list the picker reads, so the two cannot drift apart again.
4. **MIX warning on returns.**
   - Default: the ordering-intention check runs only for Provider and Replacement orders (ZKB, ZREP), not for returns.
5. **Return Type storage and old data.**
   - Default: ZKR and ZISL store the picked Return Type (`REPL`/`RETO`/`RETR`) as the special processing indicator, replacing the test value `01`.
   - Existing ZKR returns saved with `01` are not corrected under this issue; the backend team says if a correction is needed.
