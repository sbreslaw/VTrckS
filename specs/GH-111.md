## Acceptance

The change will be tested against this list.

1. **ZKR saves on the first Save.** The backend save checks are active on the dev system. A new ZKR return has all header fields filled (Return Reason, ExIS ID, ExIS Return Order Date, Shipping Condition, Description, Vaccine Return Type, No. of Boxes, Status, Contact) and one item (NDC, Lot, Expiration Date, Quantity). It saves on the first Save, with no error from the save checks, and shows its new number.
2. **The header reaches the backend before the save.** In the network trace:
   - the header values and the Contact are written to the open create session before the save request (`SaveChanges`);
   - the save request is sent on its own;
   - after it there is no further header update on the new return number.
3. **Stored as entered.** Reopening the saved return (and VA03) shows every header value and the Contact exactly as sent.
4. **A rejected save can be corrected.** If a save check still rejects the return (for example, a field it requires was left empty), Save stops:
   - the backend message is shown in the message list;
   - nothing is saved and the entries stay on screen;
   - after the correction, Save succeeds.
5. **Other return types.** ZISL, ZXFR and ZWST create and save the same way: header values before the save request, stored as entered.
6. **Unchanged.**
   - Creating a Provider Order (ZKB) sends the same requests as today.
   - Item entry during create (steps 3.3–3.6 in the request) is unchanged.
   - Editing saved returns is unchanged.
   - No new console errors.

## Out of scope

- Provider Orders (ZKB, ZREP): their create sequence stays as today (open question 1).
- The ship-to address picked during create: still written after the save (open question 3).
- Item entry during create, and editing saved returns.
- The backend save checks themselves (what they check and their messages).
- The "Document is incomplete" warning shown after saving a return.

## Open questions

Each question shows the default that is applied if it is not answered.

1. **Provider Orders too?** Their create uses the same save step and also sends its header fields after the save.
   - Default: **Returns only**; Provider Orders keep today's sequence.
   - Alternative on request: both.
2. **What the save checks read.**
   - Default: they read the header fields of step 4.3 in the request and/or the Contact, and they are switched back on in the dev system before testing.
   - If they also read other data (ship-to address, items, texts), that becomes a separate issue.
3. **Ship-to address picked during create.**
   - Default: **unchanged**, still written after the save.
   - Alternative on request: write it into the session before the save as well.
4. **A header value refused before the save.** Default: handled like a failed save today. Save stops, nothing is saved, the entries stay, the backend message is shown, and Save can be retried.
5. **Return types.** The issue ticks ZKR only, but all return types share the create path. Default: **all four** (ZKR, ZISL, ZXFR, ZWST), each tested.
